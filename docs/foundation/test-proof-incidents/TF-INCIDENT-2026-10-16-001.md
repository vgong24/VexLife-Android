## Known observability defect

This part is established independently of the unknown failure root cause.

At the time of Occurrence 001:

~~~text
verifyVexDevice
    -> depended on verifyVexDeviceResults

verifyVexDeviceResults
    -> depended on connectedDebugAndroidTest
~~~

When `connectedDebugAndroidTest` failed, Gradle stopped the dependency chain before
`verifyVexDeviceResults` could inspect the generated results.

Therefore:

~~~text
why the test failed
    UNKNOWN

why the exact failing testcase was lost
    KNOWN
~~~

Do not conflate those.

## Correlating preventive signal

During the same proof window, Android/Compose emitted deprecation guidance for:

~~~text
VexJourneyInstrumentedTest
VexScreenCrawlerInstrumentedTest
~~~

Both still used v1 `createComposeRule`.

The current Compose v2 rule uses different dispatcher semantics and is the recommended API. That made
migration reasonable preventive hardening.

It did **not** prove that scheduler behavior caused Occurrence 001.

## Hardening candidate — PR #100

PR #100 forms three repairs.

### 1. Failure-safe result inspection

~~~text
connectedDebugAndroidTest
    -> ALWAYS finalizes into verifyVexDeviceResults
~~~

The inspector forms:

`build/vex/test-foundation/device-result-summary.txt`

and reports exact retained:

- class;
- testcase;
- failure/error type;
- bounded message;
- executed/skipped/failed counts.

### 2. Evidence retention

The Test Foundation proof bundle retains:

- connected Android JUnit XML;
- connected Android HTML report when formed;
- device result summary.

### 3. Compose test realization hardening

Journey and ScreenCrawler move from deprecated v1 `createComposeRule` to the current v2 API.

This is Android/Test Foundation realization hardening, not a rewrite of Vex Journey semantics.
